# Nuke Pipeline TD: інтеграція `little_helpers/`

Аудиторія: той, хто відповідає за Nuke pipeline / спільний repo з тулзами
студії, а не окремі художники. Фіча-лист для художника і "просто спробувати
на своїй машині" — в `little_helpers/README.md`; цей документ — про те, як
вкласти той самий пакет у pipeline-керований `NUKE_PATH` замість ручного
копіювання кожним артистом собі.

## Що саме інтегруємо

`little_helpers/` — самодостатній Python-пакет для Nuke: чотири тулзи для
художників (ініціалізація layer-branch, степінг версій шарів, спліт компа
по lightgroup, repath нод при вставці з іншого шоту). **Жодної залежності
від MCP-обв'язки цього репо** — пакет
ніколи не імпортує `nuke_mcp_plugin`, не відкриває сокет, не звертається
нікуди за межі Nuke-сесії, в якій працює. Кожен імпорт всередині
`little_helpers/` — це stdlib, `nuke`, `PySide6`/`PySide2` (Qt, з фолбеком
на PySide2 для Nuke до 16-ї версії), відносний імпорт всередині самого
пакета, або (тільки в `split_layers/split_layers.py`) pipeline-овий
`pl_scripts.split_layers` — той самий підпакет, що вже стоїть на
`NUKE_PATH` під меню `Plarium > Split Layers` (`pl_scripts` лежить у
корені студійного NUKE_PATH-запису, наприклад
`.../plarium-nuke-<версія>/pl_scripts/split_layers`), деталі в §4. Саме
перше робить безпечним віддати пакет у ширший pipeline без нічого, що
припускає, що код працює саме на дев-машині (pc137), де його писали;
друге — те, чого варто саме тому свідомо очікувати при інтеграції
(`pl_scripts` має бути на `NUKE_PATH` до того, як `little_helpers`
спробує його імпортувати).

## 1. Які файли й куди класти

Репо влаштоване так, щоб його корінь можна було покласти прямо на
`NUKE_PATH` цілком, без ручного перейменування чи розпаковування — назва
папки чекауту не має значення, значення має лише вміст усередині:

```
<корінь репо, будь-яка назва на диску>/
├── menu.py               (два рядки — імпортує пакет і реєструє меню)
├── README.md
├── .gitignore
├── docs/
│   ├── NUKE_COMP_LAYER_ASSEMBLY.md
│   └── NUKE_PIPELINE_TD_INTEGRATION.md   (цей файл)
└── little_helpers/        (сам Python-пакет — оце й імпортується)
    ├── __init__.py
    ├── nuke_utils.py
    ├── hud.py
    ├── layer_branch.py
    ├── layer_picker_ui.py
    ├── repath.py             (Repath on Paste, Alt+V)
    ├── repath_ui.py          (repath-діалог, окремий модуль)
    ├── veriter/             (Change Render Version, Shift+E)
    │   ├── __init__.py
    │   ├── versions.py
    │   └── version_ui.py
    └── split_layers/        (Split Layers, F10)
        ├── __init__.py
        ├── split_layers.py  (тонка обгортка над pipeline-овим
        │                     split_layers -- див. §4)
        └── nuke_actions.py  (наш власний node-graph spacing --
                               НЕ обгортка, свідома розбіжність, див. §4)
```

`little_helpers/` (підпапка-пакет) влаштований як набір тулз: спільна
інфраструктура (`hud.py`, `nuke_utils.py`, `layer_branch.py`) лежить прямо
в корені пакета, а кожна самодостатня тулза — у своїй підпапці (`veriter/`
для Change Render Version, `split_layers/` для Split Layers). Наступні нові
тулзи очікувано підуть за тим самим патерном — ще одна підпапка поруч.

Найпростіший варіант — клонувати весь цей репо кудись, що вже є на
`NUKE_PATH` (ваше центральне місце для тулз, не `~/.nuke/` на кожній
машині окремо); `menu.py` у корені підхопиться Nuke автоматично. Якщо у
вас уже є свій спільний `menu.py` і додавати ще один файл на `NUKE_PATH`
незручно — див. §2, там ті самі два рядки для вставки у ваш файл.

Більше нічого з `vfx-mcp` (звідки цей пакет колись був виділений) тягнути
не треба — ні `nuke_mcp_plugin.py`, ні `nuke_mcp_bridge.py`, нічого з
MCP-обв'язки. Це вже окремий репо (`github.com/sandalya/little_helpers`),
без жодної залежності на той.

## 2. Підключення у ваш `menu.py`

Якщо корінь цього репо вже на `NUKE_PATH` — файл `menu.py`, що лежить
прямо в корені, підхопиться сам, нічого додатково робити не треба.

Якщо ж потрібно вписати реєстрацію у вже наявний спільний init/menu-файл
pipeline (а не додавати ще один файл на `NUKE_PATH`) — ті самі два рядки
з кореневого `menu.py`:

```python
import little_helpers
little_helpers.register_menu()
```

(лишається діючим, поки корінь цього репо — тобто батьківська папка
`little_helpers/`-пакета — сам є на `NUKE_PATH`, інакше імпорт не
резолвиться).

`register_menu()` ідемпотентний (можна безпечно викликати повторно після
reload — спочатку видаляє свої ж старі пункти меню, тож дублікатів не буде)
і чіпає лише пункти меню під `Little Helpers/...`. Він не змінює й не
видаляє нічого іншого в меню `Nodes`, тож має злитися з вашим існуючим
menu.py без конфліктів, незалежно від того, що там ще є.

## 3. Хоткеї — перевірити на конфлікти перед роллаутом

| Тулза | Хоткей | Шлях у меню |
| --- | --- | --- |
| Create Render Branch | `Shift+A` | `Little Helpers/Create Render Branch` (меню `Nodes`) |
| Change Render Version | `Shift+E` | `Little Helpers/Change Render Version` (меню `Nodes`) |
| Split Layers | `F10` | `Little Helpers/Split Layers` (меню `Nodes`) |
| Repath on Paste | `Alt+V` | `Little Helpers/Repath Paste` (меню `Nodes`) — `Edit/Paste`/`Ctrl+V` не чіпається, ніколи |

Усі чотири підбирались емпірично на чистому Nuke 16 — під час розробки
зловили один реальний конфлікт (`Shift+D`, з часом прибраний; його мовчки
перебивав вбудований байнд Nuke у меню `Viewer` на "go to next keyframe" —
інше топ-левел меню, ніж `Nodes`, тому такий конфлікт легко проґавити при
скані). `Alt+V` пройшов через дві ітерації: спершу (2026-09-11)
*перевизначав* `Edit/Paste` і забирав рідний `Ctrl+V` собі, довелось
окремо відновлювати plain-paste власною командою-копією; Sashok слушно
зауважив 2026-09-12, що це зайве — `Alt+V` і так вільний, ні з чим не
конфліктує — тож фінальний варіант: звичайний новий пункт під
`Little Helpers/...`, той самий шлях реєстрації, що й у перших трьох;
`Edit/Paste` (`Ctrl+V`) ніколи не чіпається. Перед студійним роллаутом
перевірте всі чотири хоткеї проти того, що ваш pipeline вже байндить (у
меню `Nodes`, і в будь-якому іншому топ-левел меню Nuke — `Viewer`,
`Edit` тощо). Якщо щось конфліктує — всі чотири перепризначаються в
одному місці, `little_helpers/__init__.py`'s `register_menu()`.

## 4. Реальні залежності під час роботи

- **Nuke 15+ з PySide2, або Nuke 16+ з PySide6.** Стосується `veriter/`,
  `layer_picker_ui.py` і `repath_ui.py` — кожен їхній імпорт Qt спершу
  пробує PySide6, з фолбеком на PySide2. `repath_ui.py` — перший
  по-справжньому модальний `QDialog` у пакеті (решта — фреймлес `Qt.Tool`
  попапи, що закриваються по кліку повз них); варто перевірити його
  живцем на вашій версії Nuke/PySide перед роллаутом, а не лише покластись
  на те, що решта Qt-коду вже працювала.
- **`split_layers/split_layers.py` імпортує pipeline-овий `pl_scripts.split_layers`
  напряму** (`from pl_scripts import split_layers`, той самий підпакет, чий
  `pl_scripts.split_layers.main` вже висить на меню `Plarium > Split Layers`
  — перевірено проти `menu.py`, який реєструє саме цей callable) — не власна
  копія, той самий інстанс модуля, для UI-панелі й збору списку шарів
  (`data_collect`, `SplitLayers`). Наш файл лише виключає технічні паси
  (`rgba`/`mask`/`depth`/`Zg`/`Pg`/`mv`) зі списку перед відкриттям панелі.
  Якщо у вашому pipeline `split_layers` лежить під іншою назвою чи не на
  `NUKE_PATH` за замовчуванням — цей import зламається, і його треба буде
  підправити під ваш шлях.
- **`split_layers/nuke_actions.py` — НЕ обгортка, свідома копія.** Побудова
  самого графа нод (spacing між форкнутими Shuffle-гілками, крок Merge-ланцюга
  тощо) лишається окремою локальною версією, бо canonical's spacing тут
  реально інший, а не просто застарілість форку (перевірено живим
  порівнянням скріншотів: canonical рівномірний і ширший, наша версія
  компактніша — саме так, як хотіли). Якщо canonical колись зміниться —
  ця відмінність нікуди не дінеться сама, її доведеться звіряти вручну.
- **`$FTRACK_RENDER_PATH` у середовищі артиста.** Потрібна "Create Layer
  Branch" (`Shift+A`, перелічує layer-branch папки під цим шляхом) і
  "Repath on Paste" (`Alt+V`, використовує його як точку відліку
  "поточного шоту", див. §5). Якщо ваш ftrack-лончер уже виставляє цю
  змінну кожному артисту (як на машинах, де це розроблялось), додаткової
  роботи з боку pipeline не треба. "Change Render Version" цю змінну
  взагалі не чіпає — працює з тим, що вже є в скрипті (Read-ноди/виділення).
- **Жодної мережі, зовнішніх сервісів чи інших файлів репо** поза
  pipeline-овим `split_layers`, описаним вище.

## 5. Скоуп: які тулзи прив'язані до вашої конвенції компа, а які — ні

Це важливо для розуміння, чи достатньо просто "встановити", чи це дасть
ефект лише художникам, які будують комп певним конкретним способом:

- **Create Render Branch (`Shift+A`)** прив'язана до однієї конкретної
  схеми компа — повний рецепт у `docs/NUKE_COMP_LAYER_ASSEMBLY.md`.
  Коротко: очікує рендер-структуру вигляду
  `.../render/<layer>/v0XX/<pass>_product.<frame>.<ext>` з рівно чотирма
  пасами на кожен layer-branch (`lights`, `beauty`, `tech`, `crypto`), і
  будує під це конкретний ланцюжок `ShuffleCopy`/`Copy`/`Cryptomatte`.
  Якщо структура рендеру чи стиль компа в конкретного художника відрізняється
  від цієї конвенції — ця кнопка збудує йому не те; це не універсальна
  тулза "зібрати будь-які паси".
- **Change Render Version (`Shift+E`)** універсальніша: вона реверс-парсить
  knob `file` на вже наявній (виділеній або видимій у в'юпорті) Read-ноді
  проти того самого шаблону `<layer>/vXXX/<pass>`, тож працює на будь-якій
  Read, що просто збігається з цим форматом шляху — і на тих, що зібрала
  тулза, і на ручних.
- **Split Layers (`F10`)** взагалі не залежить від layer-branch конвенції —
  працює з тим, що виділено, і його вхідними каналами, незалежно від того,
  як цю ноду будували.
- **Repath on Paste (`Alt+V`)** прив'язана до тієї ж конвенції шляхів, що
  й Change Render Version — той самий `<layer>/vXXX/<pass>_product.<frame>.<ext>`
  парсинг, і так само читає `$FTRACK_RENDER_PATH` (як Create Render Branch)
  як точку відліку "поточного шоту". Read, чий шлях не збігається з цим
  форматом, попап взагалі ігнорує — на звичайний paste не спрацьовує.

Якщо конвенція компа у вашій студії відрізняється від тієї, що в
`docs/NUKE_COMP_LAYER_ASSEMBLY.md`, Function 1 доведеться адаптувати (це
одна функція, `little_helpers/layer_branch.py:build_layer_branch()`), перш
ніж вона стане корисною по всьому pipeline — решта тулз (Change Layer
Version, Split Layers, Repath on Paste) просто нічого не роблять на
Read'ах, що не збігаються з форматом, а не ламаються, тож працюють як є
незалежно від конвенції (Split Layers — взагалі без застережень, два інші —
"мовчки неактивні", якщо шлях не той).

## 6. Оновлення

Автооновлення чи live-reload через мережу тут немає — це звичайний
Python-пакет, не сервіс. Ставтеся до нього як до будь-якої іншої вендорної
pipeline-тулзи: витягнути потрібний коміт з цього репо, скопіювати
`little_helpers/` у ваше місце для тулз — і все. `little_helpers.reload_all()`
(використовується всередині на кожне натискання хоткею — для швидкого
edit-reload циклу самого розробника) не шкодить лишити і для художників —
він просто пере-імпортує сабмодулі самого пакета, нічого зовнішнього — але
це не механізм оновлення; новий код з'являється лише коли ви заново
скопіюєте папку.

## 7. Порада щодо роллауту

Поки що це працювало лише на одній машині, на компах одного шоу. Перед тим
як вмикати для всіх — обкатайте на парі композерів на реальному шоті,
зокрема прогнавши "Create Render Branch" на вашій реальній структурі
рендер-виводу (§5) і перевіривши хоткеї (§3) проти вже наявних байндів.
Власник/супроводжуючий цього набору тулз — Sashok; питання й розбіжності в
конвенції адресувати через нього.
